# Admin Issuance Security Readiness Review

Status: **Phase 1m readiness complete; implementation not started.**

This document freezes the security and persistence boundary for a future
LaunchFlow administrator issuance system. It is a readiness review, not an
implementation, migration, signing authorization, or release authorization.

Phase 1m does not load any key, sign or verify any artifact, generate a request
or license, inspect host identity, or change current administrator, licensing,
client, build, export, or Release behavior. Windows x86_64 Beta remains the
only supported product target.

## 1. Scope and non-goals

Phase 1m freezes:

- inspect-only as the default future administrator behavior;
- explicit issuance modes and their request/container compatibility matrix;
- the administrator-side authorization authority;
- persistent replay/conflict state and transaction rules;
- a trusted signing-key metadata registry with no secret material;
- product, edition, entitlement, validity, version, identity, and mode policy;
- append-only issuance audit events and privacy masking;
- an atomic-enough, crash-recoverable issuance state machine;
- reissue, revocation, key-rotation, backup, and recovery boundaries;
- four separately authorized implementation slices.

Phase 1m does not:

- implement `LFREQ2` or `LFLIC2` parsing, encoding, signing, or verification;
- implement an administrator database, registry, state machine, UI, or CLI;
- alter `LFREQ1`, legacy requests, `lfreq-1`, `lflic-1`, legacy licenses, RSA,
  or their current parser/signature/identity order;
- implement HWID v2 or a native Linux/macOS identity;
- load a private or public key, resolve a secret reference, or invoke a signer;
- build an EXE, migrate state, publish a Release, or alter a tag.

## 2. Verified current administrator call chain

The current author-only tools are legacy-v1 production behavior and remain
unchanged by Phase 1m.

### 2.1 Entrypoints

`tools/license_admin.py` exposes:

- `inspect`
- `issue`
- `issue-dev`
- `verify`
- `history`

`tools/license_generator.py` is an older, separate interactive legacy issuer.
It does not share a durable transactional issuance state with the newer CLI.

There is no `licensing/request_code.py` in the current tree. The implemented
request codec is `licensing/request_token.py`.

### 2.2 Request inspection

The current `inspect` path is:

```text
license_admin.main
-> _read_request
-> parse_request_token
-> LFREQ1 parser or broad unprefixed legacy Base64 JSON fallback
-> _print_request
-> mask_machine_id
```

It does not call the current issuer or signer. However, the CLI imports the
admin core at module load, and the core imports legacy signing dependencies at
module load. Therefore current `inspect` avoids the signing call but is not yet
a dependency-isolated inspect-only architecture.

Current request normalization trims and uppercases `machine_id` in the request
parser, then the issuing core normalizes it again. The admin does not collect or
recalculate a customer's local identity. Legacy requests receive a derived
legacy request identifier from the current parser.

### 2.3 Current `issue` and `issue-dev` chain

The current order is:

```text
parse request
-> confirm an operator-supplied secret reference resolves to a file
-> scan local JSONL history for request_id
-> build lflic-1 payload
-> call sign_payload
-> validate_new_license_shape
-> check output suffix/parent/existing-file rules
-> write license JSON
-> append JSONL history
```

This is recorded as current behavior, not recommended future ordering. Signing
currently precedes full shape and output preflight. License file persistence and
history append are separate operations, and replay checking is a non-atomic
read-before-write. Phase 1m does not fix those production behaviors.

There is no current edition/feature relationship registry, entitlement

### 2.5 Current persistence and audit

Current duplicate detection scans a local JSONL file for exact `request_id`.
An operator `force` option can override the duplicate and output checks. The
current history contains selected issue metadata, but not a canonical request
digest, authorization record/revision, issuance mode, policy revision, public
key ID, full state transition history, artifact digest, or reissue/revocation
relationship.

The JSONL file is editable, has no database uniqueness constraint or lock, and
is appended only after the output file is written. It is useful legacy history,
not an authoritative replay ledger and not a cryptographically tamper-proof
audit system.

## 3. Administrator trust model

The future administrator system has four separate trust domains:

1. **Request input:** untrusted framing and customer-proposed context.
2. **Authorization authority:** approved administrator-side business record.
3. **Issuance policy:** versioned allowlists and validity/version constraints.
4. **Signing capability:** separately privileged signer selected only through
   trusted registry metadata after all non-secret preflight succeeds.

No domain may silently substitute for another. A valid request is not an
authorization. A policy match is not approval. A signing capability does not
choose customer rights. An interactive confirmation does not create an
AuthorizationRecord.

## 4. Inspect-only default decision

The future administrator default is exactly `inspect-only`.

- Omitting a mode means `inspect-only`, never legacy issuance.
- Supplying only a request never issues.
- Successful framing, checksum, canonical JSON, schema, request-ID, timestamp,
  product, version, or identity-algorithm parsing never issues.
- A first-seen request ID never issues.
- Interactive confirmation and a non-interactive `--yes` equivalent cannot
  replace an approved AuthorizationRecord.
- Missing, unavailable, corrupt, locked, or incompatible authoritative state
  permits bounded inspection but makes issuance fail closed.
- The inspect-only module dependency graph must not import the signer, secret
  resolver, cryptographic loader, or production issuer.
- Inspect-only performs zero replay reservations, authorization consumption,
  key resolution, signing, artifact writes, and audit mutation.

A future `dry-run` is a no-side-effect modifier, not an issuance mode. It must
still require an explicit issuance mode, approved authorization, policy match,
and trusted registry metadata, then return a redacted immutable IssuancePlan.
It performs zero reservation, consumption, key resolution, signing, or file
write.

## 5. Explicit issuance modes

The only frozen mode names are:

- `inspect-only`
- `legacy-lflic-1`
- `versioned-lflic-2`

The exact compatibility matrix is:

| Request kind | inspect-only | legacy-lflic-1 | versioned-lflic-2 |
|---|---|---|---|
| Unprefixed supported legacy request | inspect only | May produce `lflic-1` with explicit authorization | Reject |
| `LFREQ1` / `lfreq-1` | inspect only | May produce `lflic-1` with explicit authorization | Reject |
| `LFREQ2` / `lfreq-2` | inspect only | Reject | May produce `LFLIC2` with explicit authorization |
| Unknown prefix/schema | Reject | Reject | Reject |

Issuance mode is a separate trusted operator/admin-policy input. It is never
inferred from request prefix, payload schema, machine-ID length or formatting,
identity algorithm, available key, output suffix, current client version, or a
parse error. Cross-generation conversion and error-triggered legacy fallback
fail closed.

## 6. Request trust boundary

The Phase 1l request boundary remains authoritative:

- `LFREQ1`, legacy requests, and `LFREQ2` are not authorization records.
- An LFREQ checksum is damage detection, not authentication.
- `request_id` is correlation, not a credential, owner proof, freshness proof,
  or replay prevention by itself.
- A request timestamp is client-claimed time, not trusted administrator time.
- A machine or identity value is a proposed binding target, not proof that the
  requester owns the device or customer account.
- Product and app version provide review context only.
- Customer, edition, entitlements/features, validity, version range, issuance
  mode, signing profile, reissue rights, and product policy never inherit from
  a request.

For future LFREQ2 review, the canonical request digest is:

```text
SHA256(canonical LFREQ2 payload bytes)
```

Every persisted SHA-256 digest in this design uses exactly 64 lowercase ASCII
hexadecimal characters. `request_payload_digest` covers the canonical LFREQ2
payload bytes above; `policy_digest` covers the Phase 1l canonical UTF-8 JSON
bytes of the complete immutable policy revision with its own digest field
omitted; and `artifact_digest` covers the exact final artifact bytes. Empty
strings, uppercase hex, prefixes, alternate encodings, and implementation-
defined serialization are rejected. The one exception is `key_id`, whose
frozen representation is `spki-sha256:` followed by that same 64-lowercase-hex
encoding of the DER SubjectPublicKeyInfo SHA-256 digest.

The exact digest, schema, and request ID are bound to authorization/replay
state. The raw token, full identity value, email body, and request body are not
stored in ordinary audit events. At issuance, the operator supplies the request
again; the admin reparses it and requires its canonical digest to match the
approved record before copying the exact signed identity pair.

## 7. AuthorizationRecord authority

`AuthorizationRecord` is the sole authority for rights granted by a future
issuer. It is an administrator-side approved record, not a request extension.

Minimum fields:

| Field | Frozen purpose |
|---|---|
| `authorization_id` | Stable administrator identifier |
| `revision` | Immutable positive revision |
| `request_schema` | Exact approved request schema |
| `request_id` | Exact correlation ID |
| `request_payload_digest` | Canonical request SHA-256 |
| `customer_id` | Minimal opaque customer identifier |
| `customer` | Exact immutable customer text copied into the signed license payload |
| `product` | Administrator-approved product |
| `edition` | Administrator-approved edition |
| `entitlements` | Sorted unique approved entitlement set |
| `validity_duration_seconds` | Exact positive integer duration accepted by the pinned policy |
| `min_app_version` / `max_app_version` | Approved signed version range |
| `allowed_issuance_mode` | One exact explicit mode |
| `allowed_identity_algorithm` | One exact approved algorithm |
| `signing_profile_id` | One exact approved administrator signing profile |
| `request_ownership_proof_ref` | Reference to separately reviewed evidence |
| `policy_revision` / `policy_digest` | Exact policy used for approval |
| `approval_actor` | Opaque authenticated administrator principal ID; never an OS username |
| `approval_timestamp` | Trusted administrator-side time |
| `approval_reason` | Auditable reason/reference |
| `reissue_policy` | Exact one-time/reissue rule |

Customer details beyond the minimum opaque identifier belong in the external
business/authorization system, not the issuance audit. The exact `customer`
snapshot above is the minimum text authorized for the signed artifact; it is
not recovered later from a mutable customer profile.

Approval content is immutable. Mutable authorization state and an optional
revocation reference live in a separate `AuthorizationState` row keyed by
`(authorization_id, revision)` and follow Section 15.1. Approving changed
content creates a new positive revision; it never updates a previously approved
revision in place.

An operator UI may collect draft values, but issuance accepts only an approved,
immutable AuthorizationRecord revision. Bare CLI flags cannot override an
approved customer, product, edition, entitlement, validity, app-version,
identity-algorithm, mode, policy, or signing-profile decision at issue time.

Authorization approval records the administrator's external ownership and
entitlement review; it does not cryptographically authenticate the request.
Changing policy after approval requires re-review of every unconsumed
authorization pinned to an older policy revision.

Reservation creates one immutable `IssuancePlan`. Its `issued_at` is the exact
trusted administrator UTC epoch second captured by the reservation transaction,
and its `expires_at` is deterministically
`issued_at + validity_duration_seconds`, after checked-integer and pinned-policy
ceiling validation. The plan copies the exact customer, product, edition,
entitlements, app-version range, identity algorithm, issuance mode, and signing
profile from the approved revision. No field may be narrowed, substituted, or
otherwise changed at signing time. Any proposed narrowing or other change
requires a new approved AuthorizationRecord revision before reservation.

## 8. ProcessedRequestRecord and replay model

The authoritative `ProcessedRequestRecord` contains at least:

- `request_schema`
- `request_id`
- `request_payload_digest`
- `authorization_id` and revision
- `issuance_mode`
- `operation_id`
- resulting `license_id`
- processed timestamp
- operator identifier
- result status

Rules:

1. `request_id` is globally unique in the administrator registry; the primary
   semantic key remains `(request_schema, request_id)`.
2. A request ID is inseparably bound to its schema and canonical payload digest.
3. Same ID/schema and same digest is a duplicate/idempotent lookup, not a new
   authorization.
4. Same ID with a different schema or digest is an audited conflict and fails
   closed.
5. The same payload under a new request ID is not automatically entitled. It
   requires a separately matching approved authorization.
6. Future LFREQ2 replay has no `force` override. Reissue uses a new request,
   authorization, operation, and license ID.
7. Inspect-only and dry-run do not create or consume a processed record.
8. Validation/policy failures before reservation consume nothing.
9. Once reservation commits, the request and authorization remain claimed by
   that operation until explicit recovery or quarantine resolution; a failure
   never silently releases them for a second issuance.

The registry detects repeats and conflicts known to that state database. It
does not authenticate a fresh forged request with a new UUID, and a restored or
rolled-back database can lose replay knowledge. External order/ownership state,
backup discipline, and restore reconciliation remain mandatory.

## 9. Replay atomicity decision

Replay check, request claim, authorization reservation, operation creation,
and the corresponding audit event must occur in one SQLite transaction:

```text
BEGIN IMMEDIATE
-> look up request_id globally
-> classify duplicate or schema/digest conflict
-> require exact approved AuthorizationRecord revision and binding
-> atomically change authorization approved -> reserved
-> insert ProcessedRequestRecord under uniqueness constraints
-> insert IssueOperation in reserved state
-> append reservation audit event
COMMIT
```

The implementation must rely on database uniqueness and conditional updates,
not a separate check-then-insert. Lock timeout, database unavailability,
integrity error, schema mismatch, or concurrent conflict fails closed.

Exactly one concurrent claimant may reserve a request and authorization. Other
claimants observe duplicate/conflict/consumed state and perform zero key access,
signing, or output writes.

## 10. Storage options reviewed

| Option | Transactions/uniqueness | Concurrency/crash recovery | Audit/backup | Operations | Decision |
|---|---|---|---|---|---|
| stdlib SQLite | ACID transactions, constraints, conditional updates | One-writer serialization, WAL/rollback recovery | Queryable events, online backup API | Local, no new dependency | **Recommended authoritative store** |
| Append-only JSONL | No cross-record uniqueness or atomic claim | Locking and torn-tail recovery are custom | Human-readable append/export | Simple, but unsafe as authority | Reject as authority; optional redacted export only |
| Single JSON file | Whole-file rewrite; no native constraints | High lost-update/corruption risk | Easy copy, hard safe merge | Simple only at tiny scale | Reject |
| Filesystem lock plus JSON | Lock is not a data model or transaction | Stale locks and multi-file crash windows | Custom reconciliation | Platform-sensitive complexity | Reject |
| External database/service | Strong transactions possible | Adds service/network/credential failure modes | Potentially strong | Excessive for offline author-only Beta | Defer; not the minimum local design |

## 11. Recommended storage decision

Use Python stdlib `sqlite3` as the single authoritative administrator state.

Future schema migration `0 -> 1` must create, at minimum:

- schema metadata;
- authorization records and immutable revisions;
- processed requests;
- issuance operations;
- immutable issuance plans and canonical output-target claims;
- trusted signing-key metadata;
- versioned policy records;
- append-only issuance audit events;
- license lifecycle/reissue/revocation relationships.

Required properties:

- foreign keys enabled;
- explicit schema version and transactional migrations;
- global request-ID uniqueness plus exact schema/digest binding;
- unique operation and license IDs;
- one canonical relative output target per operation and a uniqueness constraint
  preventing two operations from claiming the same target;
- conditional authorization state transition;
- `BEGIN IMMEDIATE` for claims;
- bounded busy handling and fail-closed lock errors;
- production durability settings selected and documented;
- SQLite backup API plus backup verification;
- no automatic import of legacy JSONL as authoritative replay state;
- database location, access control, retention, and operator backup procedure
  decided before production use.

JSONL may be a redacted, regenerated audit export. It is never the source used
to authorize, deduplicate, resume, or revoke issuance.

## 12. Trusted signing-key registry

`TrustedSigningKeyRecord` contains only non-secret metadata:

- `profile_id`
- `signing_algorithm`
- `key_id`
- `public_key_spki_sha256`
- opaque private-key reference identifier
- allowed issuance modes
- allowed product
- `active_from`
- `retired_at`
- status

`key_id` is exactly `spki-sha256:` plus `public_key_spki_sha256`.
`public_key_spki_sha256` is exactly the 64-lowercase-hex SHA-256 digest of the
public key's DER SubjectPublicKeyInfo; a mismatch rejects the record before it
can become active. `profile_id` is the only identifier referenced by policy and
AuthorizationRecord. It is not a key path or secret reference.

This administrator registry authorizes eligibility for future signing only.
It is separate from, and cannot add to or modify, the Phase 1l client
verification registry compiled into the client or authenticated by the same
client-release trust chain. Enabling an administrator profile never causes an
installed client to trust its key; adding client trust requires a separately
reviewed trusted client release. Conversely, a client verification entry does
not authorize administrator signing.

Rules:

1. Selection uses one exact `(signing_algorithm, key_id)` pair.
2. Unknown, disabled, future, expired, retired-for-issuance, or incompatible
   entries fail closed before secret resolution.
3. There is no default key, try-all, algorithm fallback, partial ID, or
   signature-length key guessing.
4. `key_id` and the opaque secret-reference identifier are never interpreted
   as a request/customer supplied path, URL, environment variable, Registry
   location, user-writable config, or network location.
5. Request, customer, and raw operator input cannot select a key.
6. Authorization/policy select an approved signing profile; the profile binds
   exact algorithm/key metadata.
7. The registry contains no private-key body, password, or secret location.
8. Before later signing, the privileged signer must prove its public identity
   matches the registry entry without logging secret material.
9. Rotation adds a new immutable record and key ID; historical IDs are not
   rewritten.
10. A retired key cannot sign new licenses by default. A client may continue
    verifying old licenses with its already trusted public entry according to
    release policy.
11. A compromised key immediately disables new admin issuance, but offline
    clients require a separate trusted update/revocation strategy. Phase 1m
    makes no instant-revocation claim.

Signing-profile lifecycle is exact: `proposed -> active -> retired`, and either
`proposed` or `active` may transition to `disabled-compromised`. `retired` and
`disabled-compromised` are terminal for new signing. Reactivation or correction
requires a new immutable profile record; it never edits or re-enables the old
record. Creation, activation, retirement, and compromise disablement require an
opaque authenticated administrator principal and append an audit event in the
same SQLite transaction as the state change.

## 13. Policy registry

The administrator PolicyRegistry is versioned, immutable by revision, and
pinned by AuthorizationRecord. It defines:

- product allowlist;
- edition allowlist;
- allowed edition-to-entitlement relationships;
- sorted, unique entitlement token rules;
- validity ceilings and whether perpetual licensing is allowed;
- minimum/maximum app-version constraints;
- identity-algorithm allowlist;
- issuance-mode allowlist;
- signing-profile allowlist;
- activation date, retirement date, status, revision, and digest.

Unknown product, edition, entitlement, identity algorithm, mode, policy
revision, or signing profile fails closed. An approval may authorize values
that are equal to or narrower than the selected policy bounds, but once that
AuthorizationRecord revision is approved its exact entitlement set, validity
duration, and app-version range are immutable issuance inputs. Any later
reduction, narrowing, or substitution requires a new approved revision; the
issuer and signer never make that choice.

The frozen `lflic-2` shape requires a finite `expires_at`; perpetual LFLIC2 is
therefore not permitted without a separately versioned schema. Versioned
issuance never falls back to legacy identity. Legacy issuance remains possible
only through explicit `legacy-lflic-1` authorization and does not change current
v1 parsing or client verification.

The concrete production editions, entitlement names, validity ceilings,
ownership evidence, quotas, and signing profiles remain product decisions and
are not invented by Phase 1m.

## 14. IssuanceAuditRecord

Every persisted transition appends an application-level immutable audit event
in the same SQLite transaction as that state change. Minimum event fields:

- audit event ID and monotonic sequence;
- authorization ID/revision;
- request schema, request ID, and canonical request digest;
- operation ID and license ID;
- issuance mode and identity algorithm;
- masked identity value;
- product, minimal customer ID, edition, and entitlement names;
- issued/expires values;
- public signing key ID/profile ID;
- policy revision/digest;
- opaque administrator principal ID and trusted administrator timestamp;
- event/action, old state, new state, reason, and result status;
- output artifact digest;
- optional supersedes/reissues/revokes relationship.

The audit must not contain:

- raw MachineGuid or volume output;
- hostname or username;
- complete machine/identity value;
- complete request token or payload;
- complete license or signature;
- private-key material, password, secret reference, or secret location;
- mail body or unnecessary customer personal details.

Mask rule: retain the identity algorithm separately. For a canonical identity
value longer than eight characters, retain exactly the first four and last four
characters separated by `...`; for eight or fewer characters, replace every
character with `*`. Logs and ordinary errors never expose the original value.

The audit event schema is fixed. A field that is not yet known or is not
applicable to that transition is SQL `NULL`; redacted JSONL export emits an
explicit JSON `null` rather than omitting the field or inventing an empty-string
sentinel. In particular, `artifact_digest` is `NULL` before a durable artifact
exists, and relationship fields are `NULL` when the event is not a lifecycle
operation. Principal IDs are explicit opaque administrator identifiers and
must never be populated from the host OS username, hostname, or account name.

SQLite triggers or repository permissions should reject audit update/delete in
normal application use. This is application-level append-only evidence, not a
cryptographic claim that a local administrator cannot tamper with their own
machine. Backup, access control, retention, and external export policy remain
operational controls.

## 15. Atomic issuance state machine

The future design uses related state machines rather than one overloaded flag.

### 15.1 Authorization states

An editable `draft` is not an AuthorizationRecord. Approval creates one
immutable AuthorizationRecord revision and a separate conditional state row.
The only allowed authorization transitions are:

| From | To | Exact condition |
|---|---|---|
| `draft` | `approved` | authenticated approval creates and pins one immutable revision |
| `draft` | `rejected` | authenticated rejection with reason |
| `approved` | `reserved` | the Section 9 transaction binds exactly one operation |
| `approved` | `expired` | trusted administrator time exceeds the approval lifetime |
| `approved` | `revoked-before-use` | authenticated revocation before reservation |
| `approved` | `superseded` | a separately approved replacement revision is selected |
| `reserved` | `consumed` | the same operation completes in the Section 16 final transaction |
| `reserved` | `abandoned` | manual reconciliation proves the same operation cannot safely complete |

`rejected`, `expired`, `revoked-before-use`, `superseded`, `consumed`, and
`abandoned` are terminal for that revision. `reserved` never returns to
`approved`; a failed or quarantined operation retains its claim until that same
operation completes or is explicitly abandoned. Any later issuance requires a
new request and a new approved revision.

### 15.2 ProcessedRequest states

Inspection is transient and creates no ProcessedRequestRecord. Reservation
creates the record directly in `reserved`. Its only allowed transitions are:

| From | To | Exact condition |
|---|---|---|
| `reserved` | `completed` | the bound IssueOperation completes |
| `reserved` | `quarantined` | signer, artifact, output, or database state becomes ambiguous |
| `quarantined` | `completed` | reconciliation proves the exact bound artifact and operation |
| `quarantined` | `abandoned` | reconciliation cannot safely complete the bound operation |

`completed` and `abandoned` are terminal, and both permanently consume the
request key. The row and its unique `(request_id, request_schema, digest)`
binding are never deleted or released for another issuance. A same-ID
schema/digest conflict appends a separate terminal conflict audit record and
does not replace or mutate the authoritative ProcessedRequestRecord. An exact
duplicate is an idempotent status lookup and causes no state transition.

### 15.3 IssueOperation states

The only allowed IssueOperation transitions are:

| From | To | Exact condition |
|---|---|---|
| `reserved` | `signing` | all non-secret preflight still passes; transition commits before signer entry |
| `reserved` | `failed` | deterministic pre-sign failure with no signer entry |
| `failed` | `reserved` | explicit audited retry of the same IDs after the deterministic cause is fixed |
| `failed` | `abandoned` | authenticated decision not to retry |
| `signing` | `signed` | one matching temporary artifact is durable and its digest is committed |
| `signing` | `quarantined` | crash, signer error, or uncertainty after signer entry |
| `signed` | `persisted` | the same artifact is finalized under the no-clobber rules |
| `signed` | `quarantined` | artifact missing, mismatched, or finalization ambiguous |
| `persisted` | `completed` | processed request, authorization, lifecycle, and audit commit together |
| `persisted` | `quarantined` | final artifact or database completion becomes ambiguous |
| `quarantined` | `signed` / `persisted` / `completed` | manual reconciliation proves the exact same artifact, digest, target, and operation; signer is never called |
| `quarantined` | `abandoned` | reconciliation cannot prove a safe continuation |

`completed` and `abandoned` are terminal. A crash or exception while state is
`signing` is always ambiguous even if secret resolution may have failed before
the signer produced bytes; it enters `quarantined` and never automatically
calls the signer again. Every transition uses a conditional old-state update
and appends its audit event in the same SQLite transaction.

### 15.4 LicenseLifecycle states

A lifecycle row is created as `issued` only when its IssueOperation completes.
The only later transitions are `issued -> superseded`, `issued -> revoked-local`,
or `issued -> expired-recorded`. Those three states are terminal for that
license record. `reissued` is an audit relationship from a newly issued license
to a prior license, not a state and not permission to restart either operation.
None of these administrator states changes an already installed offline
artifact without a separately designed trusted client channel.

### 15.5 Retry and terminal invariants

- Failures before reservation create no claim and may be retried normally.
- A known pre-sign `failed` operation may retry only through `failed -> reserved`
  with the same operation, authorization, request, license ID, and output target.
- Recovery from `signed` or `persisted` uses only the matching artifact and
  digest; it never signs again.
- `abandoned` never releases a request or authorization for reuse. A legitimate
  later attempt follows the reissue policy with a new request and authorization.
- No terminal state is edited, deleted, or reset. Corrections are new records
  and linked audit events.

## 16. Artifact persistence and crash recovery

SQLite and the filesystem cannot share one real transaction. The design uses a
staged recovery protocol and states this limitation explicitly:

The configured administrator output root is trusted configuration, never a
request or AuthorizationRecord field. The final canonical relative target is
derived exactly as `<license_id>.lic`; the IssueOperation persists that target
and uniquely claims it during reservation. It rejects absolute paths, parent
traversal, alternate spellings, and any target outside the configured root.
The temporary relative name is derived only from the fixed license and
operation IDs.

1. Complete request, authorization, policy, registry, output, and collision
   preflight before key access.
2. Atomically reserve request/auth, fixed operation/license IDs, and the unique
   canonical output target in SQLite.
3. Persist `signing` immediately before later secret resolution/signing.
4. A later separately authorized signer produces one artifact for that fixed
   operation.
5. Write to an operation-specific temporary file in the final directory,
   flush/fsync it, and calculate its SHA-256.
6. Persist `signed` plus artifact digest in SQLite.
7. Finalize with a platform-proven atomic no-clobber operation and fsync the
   containing directory where supported. An overwrite-capable ordinary replace
   is forbidden.
8. Verify the final artifact digest.
9. In one SQLite transaction, mark the operation/processed request completed,
   consume the authorization, create license lifecycle state, and append audit.

Crash handling:

| Crash/failure point | Required outcome |
|---|---|
| Before reservation | No state consumed; normal retry allowed |
| Reservation committed, before signer entry | Same operation may be explicitly resumed |
| During/after signer entry, before durable matching artifact | Quarantine; never silently re-sign |
| Temporary artifact durable, SQLite `signed` update failed | Quarantine and reconcile digest; never create a new license ID |
| SQLite `signed`, no-clobber finalization not completed | Retry only the same temp-file promotion after digest match |
| Final target exists, final DB completion missing | Continue only when the target is uniquely claimed by this operation and its exact digest matches; otherwise quarantine without overwrite |
| Temp/final artifact missing or digest mismatched | Quarantine; do not release request reservation |
| Audit/final transaction fails | Operation remains persisted/reserved for same-operation recovery |

Temporary filenames contain only the operation identifier, never customer,
identity, request, key, or entitlement data. Cleanup never deletes an ambiguous
artifact automatically. The finalizer never replaces an existing non-matching
file. A pre-existing matching file is recovery evidence only when SQLite binds
the same target to the same operation and stored artifact digest; digest match
alone cannot transfer ownership between operations.

## 17. Reissue, revocation, rotation, and recovery boundaries

### Reissue/reactivation

- Require a new request, new approved AuthorizationRecord, new operation, and
  new license ID.
- Link the known prior license only through audit/lifecycle `supersedes` data.
- Never edit or resign an existing artifact in place.
- Never use a partial identity match, candidate list, old request replay, or
  cross-generation conversion.

### Revocation

- Revoking an unused authorization prevents reservation.
- Revoking/expiring an authorization after consumption does not silently revoke
  an already signed license.
- Administrator license revocation is local business state. An offline client
  does not learn it without a separately designed trusted channel/update.
- Revocation cannot be represented by deleting history.

### Key rotation/compromise

- Rotation adds a new `proposed` metadata record/profile, then requires the
  separately audited `proposed -> active` transition.
- Retired keys remain historical verification references as policy requires but
  cannot issue new licenses by default.
- Compromise disables new signing and triggers a separate client/reissue/product
  response; it does not rewrite history or imply instant offline revocation.

### Backup/restore

- Back up SQLite with its supported backup API and verify the backup.
- Back up finalized artifacts and compare stored digests.
- After restoring older state, block issuance until reconciliation against
  newer audit/artifact evidence completes.
- Never assume an old backup still contains complete replay knowledge.

## 18. Implementation slices

The following phases must remain separate commits and reviews.

### Phase 1n — values and SQLite schema 0 -> 1

- Implement stdlib-only enums/value objects, schema migration, repositories,
  exact digest encodings, immutable authorization/plan/profile revisions,
  the four state machines, output-target uniqueness constraints,
  state-transition validation, and in-memory/file-isolated tests.
- No key loading, signing, artifact production, v1 parser change, AppData use,
  or production issuance.

### Phase 1o — inspect-only dispatch and authorization/replay transaction

- Implement strict parser dispatch, default inspect-only behavior, explicit
  mode selection, AuthorizationRecord/policy review, atomic request reservation,
  exact customer/profile/validity plan derivation, conflict classification,
  dry-run plan, and concurrency/crash injection tests.
- Inspect code must not import the signer/key loader. No signing.

### Phase 1p — synthetic signer seam and atomic artifact persistence

- First freeze a production-file allowlist and a synthetic signer contract.
- Test only an injected synthetic signer seam and synthetic artifact bytes,
  trusted metadata selection, unique canonical targets, no-clobber temporary-
  file/digest/finalization recovery, and every crash point.
- Access to any real or temporary cryptographic key/signature requires separate
  explicit authorization. Production signing remains disabled.

### Phase 1q — explicit versioned LFLIC2 issuance consideration

- Only after 1n/1o/1p acceptance may a separate task consider connecting
  LFLIC2 issuance to exact `versioned-lflic-2` mode.
- It must preserve v1 byte/behavior compatibility, the Phase 1l validation
  contract, the trusted registry, and production policy decisions.
- It is still not Release authorization and does not implement HWID v2.

The phases must not be merged into one change.

## 20. Readiness conclusion and open product decisions

Phase 1m readiness is complete. The unique recommended authority is an
administrator-only stdlib SQLite database with explicit modes, immutable
AuthorizationRecord revisions, exact replay/digest binding, trusted key/policy
metadata, transactional claims/audit, and staged artifact recovery.

The following remain unresolved implementation/product inputs:

- concrete product editions and entitlement relationships;
- validity ceilings, quotas, perpetual policy, and support duration;
- acceptable request ownership evidence and operator authentication;
- signing-profile entries and lifecycle operations;
- database location, access control, retention, backup, and disaster recovery;
- license revocation communications and offline limitations;
- production migration from the current JSONL history;
- HWID v2 and real-host evidence.

No administrator infrastructure, replay protection, trusted registry, signing,
LFLIC2 issuance, migration, or HWID v2 is implemented by this review.
